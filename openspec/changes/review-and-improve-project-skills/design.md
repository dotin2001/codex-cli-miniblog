## Context

See `proposal.md` for motivation and scope. The current repo has two local skill homes:

- `.codex/skills`: MiniBlog-specific skills for project orchestration, frontend work, and backend work.
- `.agents/skills`: generated OpenSpec workflow skills for explore, propose, apply, update, sync, and archive.

The MiniBlog skills match the current package/runtime facts observed in `apps/web/package.json`, `apps/api/requirements.txt`, `docs/architecture.md`, and the app `AGENTS.md` files. The main gap is discoverability and maintenance policy: top-level docs describe `.codex` but do not clearly explain `.agents/skills` or Codex `$openspec-*` invocation, which can make unsupported slash aliases look valid.

There are no existing main OpenSpec specs, so this change adds `project-skill-governance` as the first capability spec.

## Goals / Non-Goals

**Goals:**

- Make the local skill inventory explicit and easy to route.
- Keep MiniBlog skills concise, procedural, and grounded in durable docs.
- Clarify Codex OpenSpec invocation syntax and the limits of unsupported slash aliases.
- Preserve generated OpenSpec workflow behavior unless there is an intentional local patch.
- Add a repeatable review and validation path for future skill maintenance.

**Non-Goals:**

- No frontend, backend, API, database, auth, Docker, or runtime behavior changes.
- No rewrite of all skill files just for style.
- No new skill framework or plugin installation.
- No broad edit to generated OpenSpec workflow mechanics unless a concrete defect is confirmed during implementation.
- No change to OpenSpec schemas or `openspec/config.yaml` unless review finds that current config is blocking skill governance work.

## Decisions

### Put durable project facts before skill edits

Skill maintenance should first update `AGENTS.md`, `.codex/project.md`, and relevant `docs/*` files when a project fact is missing or stale. MiniBlog skills should then point at those docs and keep only task-routing rules, non-obvious project constraints, and verification guidance.

Rationale: durable docs are the source of truth for humans and agents. If skills become the only place a fact exists, the next app change can leave docs and skills inconsistent.

Alternative considered: update only `SKILL.md` files. That is faster, but it keeps the command-routing confusion in the project documentation.

### Treat `.codex/skills` and `.agents/skills` differently

Use `.codex/skills` for MiniBlog-owned project skills that should evolve with the repo. Treat `.agents/skills` as installed OpenSpec workflow skills generated by the OpenSpec CLI or installer.

Rationale: MiniBlog skills are project-maintained guidance. OpenSpec skills describe workflow mechanics and may be regenerated. Editing generated workflow text can create local drift from the installed OpenSpec version.

Alternative considered: merge all guidance into one skill home. That would blur ownership and make future regeneration or updates harder to reason about.

### Prefer documentation over generated workflow edits

Document OpenSpec workflow usage in repo-maintained docs and MiniBlog orchestration guidance. Only edit `.agents/skills/openspec-*.md` when a specific local issue cannot be fixed through documentation or reinstalling/regenerating OpenSpec skills.

Rationale: the earlier command issue was about unsupported command syntax, not broken workflow logic. Project docs can explain that Codex skill invocation uses `$openspec-*`, while `/opsx:*`, `/opsx-*`, and `/openspec-*` slash commands depend on the host environment.

Alternative considered: edit every generated OpenSpec skill to remove non-Codex command examples. That may reduce local confusion, but it risks fighting generated upstream content.

### Validate skills with lightweight checks

For changed MiniBlog skills, use a combination of:

- `rg --files .codex/skills .agents/skills -g 'SKILL.md'`
- manual review against durable docs and package files
- the system skill validator when available, for example `/Users/macbookpro/.codex/skills/.system/skill-creator/scripts/quick_validate.py <skill-folder>`

For changed OpenSpec workflow skills, also verify the installed OpenSpec CLI still recognizes the workflows through `openspec status`, `openspec instructions`, or the workflow-specific command paths relevant to the edited text.

Rationale: skill quality is mostly semantic, so validation should catch structural errors without pretending a parser can prove the guidance is correct.

Alternative considered: add a custom repo validator script. That is not necessary unless skill maintenance becomes frequent enough to justify automation.

## Risks / Trade-offs

- Generated OpenSpec skill edits may be overwritten by reinstalling OpenSpec -> prefer repo docs and MiniBlog-owned skills for local guidance.
- Over-documenting command syntax can become stale if the host adds slash commands later -> phrase slash commands as host-dependent instead of permanently unsupported everywhere.
- Skill guidance can duplicate docs and drift -> keep skills procedural and point to durable docs for detailed facts.
- A spec for agent behavior is less user-facing than product behavior -> keep requirements observable through docs, skill routing, and validation reports.
- Validator availability can vary across machines -> make validator use preferred when present and document manual fallback checks.

## Migration Plan

1. Audit `.codex/skills/*/SKILL.md`, `.agents/skills/openspec-*/SKILL.md`, `.codex/project.md`, `AGENTS.md`, app `AGENTS.md`, and relevant docs for stale facts or unclear routing.
2. Update durable docs first to include the skill inventory, ownership split, Codex OpenSpec invocation syntax, and maintenance order.
3. Update MiniBlog-owned skills only where they need clearer routing, skill maintenance workflow, or reduced duplication after docs change.
4. Review generated OpenSpec skills and edit them only if a concrete local defect remains after doc updates.
5. Validate changed skill folders with the system skill validator when available and perform manual checks for frontmatter, descriptions, routing, and placeholders.
6. Run no frontend/backend app tests unless implementation unexpectedly changes app code; this change should be verified through documentation/skill validation and OpenSpec status.

Rollback is a normal revert of documentation and skill-file edits. There is no runtime data migration.
